## 1. 즉시 수정한 문제

### [P1] 복습 세션 제한 전에 모든 본문 다운로드
- **위치·호출 경로:** `src/routes/review/+page.svelte` `start` → `loadDashboard` → due metadata → `getQuestion` 전체 → `LearningRepository.getReviewQueue` → `slice(reviewLimit)`.
- **현재 동작·숨은 전제:** 후보가 적을 때는 큰 비용이 없었으나 요청 수가 후보 수 U에 비례했고, 상태를 두 번 전체 읽었다. 한 세션에서는 상한 50개의 본문만 실제 사용한다.
- **규모·실제 비용:** 기존 본문 네트워크/파싱/메모리는 현재 최악 U ≤ 1,190, 콘텐츠 10배 U ≈ 11,900, 100배 U ≈ 119,000. 실제 due 수는 사용 이력에 따라 달라진다. DB도 질문 상태 Q 전체를 두 차례 읽었다. 변경 뒤 본문은 `min(U, reviewLimit)`개, 상태 조회는 후보 ID만 `bulkGet` 두 차례, 정렬 CPU는 여전히 O(U log U)다.
- **증상:** 복습 시작 대기, 일시적인 메모리 증가, 요청 폭주 또는 일부 요청 실패로 세션 전체 실패.
- **수정·회귀 방지:** metadata로 revision 조정·우선순위 정렬 후 limit를 적용하고 선택 본문만 읽는다. 본문의 ID·revision·lessonId·type을 검증한다. 100개 후보에서 한도 3개만 로드하는 테스트, metadata만 사용하는 상태 조회 테스트, revision 이벤트 재시도 중복 방지 테스트를 추가했다. **확신도: High.**

### [P1] 캐시 쓰기 실패가 정상 네트워크 응답을 가림
- **위치·호출 경로:** `src/service-worker.ts` `fetch` → `cacheFirst` → 성공한 `fetch` → `cache.put` 실패 → 기존 바깥 `catch` → `Response.error()`.
- **숨은 전제·규모:** Cache Storage가 항상 쓰기 가능하다는 전제. 캐시가 커지거나 quota가 작아지면 실패 가능성이 커진다. 실패 요청 한 건당 성공 응답 한 건이 사용 불가해졌다.
- **증상:** 연결돼 있고 서버가 성공 응답을 보냈는데도 콘텐츠 로딩 오류. 캐시 쓰기 실패만 분리해 성공 응답을 반환하도록 수정했다. 쓰기 거부 모형 테스트를 추가했다. **확신도: High.**

### [P2] 콘텐츠 파일 재탐색
- **위치·호출 경로:** `scripts/content/model.ts` `loadSourceContent` → 레슨마다 모든 파일에서 question/content 검색 → validate, quality, build, tests.
- **숨은 전제·규모:** 레슨 L, 파일 F일 때 약 2LF회 파일명 검사. 현재 2 × 236 × 2,138 ≈ 1,009,000회, 10배 규모는 약 1억 회, 100배는 약 100억 회. 파일 읽기 자체와 YAML 파싱 비용은 별도다.
- **증상:** 콘텐츠 추가 후 검증과 CI 시간 급증. 한 번 순회해 레슨별 파일을 모으고 기존 정렬을 유지하도록 수정했다. corpus의 질문·Markdown 매핑과 순서를 검사한다. **확신도: High.**

### [P2] verify의 중복 컴파일
- **위치·호출 경로:** `package.json` `verify` → `content:build` → `build` → 다시 `content:build`. CI와 Pages 배포 모두 verify 호출.
- **숨은 전제·규모:** 매회 전체 원본 2,138개를 두 번 처리. 10배·100배에서도 중복 계수 2가 유지된다. `verify`의 마지막 단계를 `vite build`로 바꾸고 직접 `npm run build`의 콘텐츠 생성은 유지했다. 전체 verify가 이 경로를 검증한다. **확신도: High.**

## 2. 다음에 수정해야 할 문제

### [P2] 대기 중인 서비스 워커의 버전별 전체 캐시 누적
- **위치·경로:** `src/service-worker.ts` `install`은 버전별 shell/content를 생성하고 모든 generated 파일을 캐시한다. 이전 버전 삭제는 `activate`에서만 한다. 오래 열린 탭에서 v2, v3가 차례로 대기하다 교체되면 대기하던 v2의 Cache Storage 항목은 정리되지 않는다.
- **현재·10배·100배:** 설치 한 번의 JSON이 약 1,430개/2.35 MB이며 빌드 자산 등은 추가된다. 대기 버전 수 V와 콘텐츠 크기 S에 비례해 O(VS) 캐시가 쌓인다. 10배·100배 콘텐츠라면 버전당 저장량도 선형 증가한다.
- **실제 비용·증상:** 설치 네트워크/저장 공간과 업데이트 시간 증가, quota 초과로 신규 오프라인 버전 설치 실패. 활성 버전을 install에서 지우면 오프라인 앱을 망가뜨릴 수 있으므로 이번 패치에서 지우지 않았다. **후속:** 활성·대기 버전 소유권을 구별한 정리 정책과 연속 대기 버전 모형 테스트. **확신도: High(캐시 경로), Medium(브라우저별 발생 빈도).**

### [P2] 긴 기록의 백업 복원 요청 증폭
- **위치·경로:** 설정 복원 → `LearningRepository.importBackup`에서 전체 이벤트를 검증·정렬·bulkAdd한 후 이벤트별 QuestionState/LessonState 조회·쓰기, GameEvent/Outbox 개별 쓰기를 하나의 트랜잭션에서 반복한다.
- **현재·10배·100배:** 이벤트 E에 비례하는 replay는 필요하나 IndexedDB 요청도 E에 비례해 여러 번 발생한다. 이벤트 10만 ~ 100만 개에서 지연·transaction 부담이 명확해진다. 백업 JSON 파싱과 메모리 사용도 E에 비례한다.
- **증상:** 장기 사용자의 복원 대기 또는 실패. **후속:** 순서 있는 replay 결과를 메모리 맵에 축적하고 최종 상태를 bulkPut하되 interleaved revision·completion 이벤트의 결과와 원자성을 기존 구현과 대조하는 테스트/벤치마크를 선행한다. **확신도: High(비용), Medium(안전한 수정 범위).**

### [P2] 화면별 필요량과 무관한 전체 스냅샷
- **위치·경로:** `getSnapshot`은 모든 lesson/question state를 `toArray` 후 JSON 깊은 복제한다. 대시보드, 레슨 진입, 설정에서 호출되지만 설정은 settings만, 레슨은 lessonStates만 사용한다.
- **현재·10배·100배:** 학습된 질문 Q와 레슨 L에 비례한 DB 읽기/메모리 복제를 화면 진입마다 수행한다. 현재 Q ≤ 1,190이며 10배/100배 콘텐츠와 장기 사용 시 Q도 늘어난다.
- **증상:** 화면 전환 지연과 메모리 압박. **후속:** 목적별 좁은 조회 API를 추가하고 설정·레슨에서 questionStates 전체 읽기를 금지하는 테스트. 복습 후보 계산은 기존 상세 상태를 유지한다. **확신도: High(경로), Medium(현재 사용자 영향).**

## 3. 확인했지만 문제 아니었던 영역

- 대시보드가 모든 lesson/question 본문을 읽는다는 과거 문제는 main에서 이미 해결됐다. catalog·curriculum·상태만 읽는다.
- 서비스 워커의 전체 generated precache 자체는 방문하지 않은 레슨까지 오프라인 사용해야 한다는 명세의 선택이다. 배치 크기 12도 기존 테스트로 확인된다.
- 백업 export의 전체 JSON 직렬화는 사용자가 요청한 전체 백업의 본질적인 비용이고 상시 실행 경로가 아니다. 현재 수정 대상에서 제외했다.
- DAG의 상태 조회 반복과 진행도 렌더의 중첩 탐색은 현재 236개 레슨, 트랙별 작은 노드 수와 화면 호출 빈도를 감안할 때 P0 ~ P2 근거가 부족하다.
- 복습 중 `suspended` 상태의 revision 변경은 다시 학습 대상으로 바뀌지만 현재 suspend UI가 없어 실사용 장애로 올리지 않았다. 변경 전 정책 명세가 필요하다.

## 4. 구조적 안전장치

- 복습 시작의 본문 로딩 수 ≤ `reviewLimit` (100개 후보/한도 3개 테스트).
- 복습 queue는 metadata로 재조정하고 후보 ID에 대해서만 IndexedDB 상태를 조회한다. revision 재시도는 중복 이벤트를 만들지 않는다.
- 선택된 question 본문은 catalog의 ID·revision·lessonId와 일치하고 type 필드가 유효해야 한다.
- 네트워크 응답이 성공하면 runtime `cache.put` 실패가 응답을 실패로 바꾸지 않는다.
- 빌드 입력은 레슨별 질문/Markdown 매핑과 정렬을 유지한다.
- verify에서 콘텐츠 컴파일은 한 번 실행하며, 독립 실행 `npm run build`는 자체적으로 콘텐츠를 생성한다.

Astra 검토: 복습 queue의 metadata 경계·revision 동시성, 서비스 워커 캐시 수명·활성 버전 보존. 실제 브라우저에서 장기 대기 업데이트와 대규모 사용자 기록 벤치마크는 아직 수행하지 않았다.
