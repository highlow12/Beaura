## 스키마는 DBMS가 검사하는 실행 계약

스키마는 구조를 설명하는 문서에 그치지 않습니다. `NOT NULL`, `UNIQUE`, `CHECK`, 외래 키 같은 제약은 DBMS가 모든 쓰기 요청마다 검사하는 실행 계약입니다. 화면에서 입력을 막았더라도 다른 클라이언트나 버그 난 배치 작업이 직접 쓰기를 시도할 수 있으므로, 데이터 자체를 지켜야 하는 규칙은 DBMS의 경계에 두는 편이 안전합니다.

```sql
CREATE TABLE Account (
  id INTEGER PRIMARY KEY,
  balance INTEGER NOT NULL CHECK (balance >= 0)
);

INSERT INTO Account VALUES (1, -10); -- CHECK 위반으로 거부
```

작은 예에서도 `balance`가 음수가 되는 경로를 DBMS가 차단합니다. 대신 제약을 엄격하게 추가하면 기존 잘못된 데이터를 먼저 정리해야 하고, 스키마를 바꾸는 마이그레이션 동안에는 오래된 클라이언트와의 호환성을 고려해야 합니다.

### 자주 틀리는 포인트

애플리케이션에서 한 번 검사했다는 이유로 DBMS 제약을 생략하면 안 됩니다. 두 클라이언트가 동시에 같은 규칙을 검사한 뒤 쓰는 순간에는 둘 다 통과할 수 있기 때문입니다. 반대로 DBMS가 화면과 업무 흐름까지 대신 설계하는 것도 아닙니다. DBMS는 데이터 상태의 경계를 지키고, 애플리케이션은 그 결과를 사용자 흐름으로 해석합니다.
